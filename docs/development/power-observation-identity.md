# Power snapshot observation identity

Issue #402 corrects historical content deduplication: a source that reports A, then B, then A must end at A, and a newly measured unchanged value must retain its new source observation time. Public payloads, routes and response fields stay unchanged. This is a persistence correction; it does not authorize deployment or enable another producer.

## Snapshot semantics and source evidence

| Snapshot | Meaning of a submitted timestamp | Persistence and latest-state behavior |
|---|---|---|
| Inverter detail | One measured inverter observation, aligned with its power reading. `Eg46500ExTelemetrySource` constructs detail at `observedAtUtc`; `PowerOutboxWriter` requires matching source/device/time in the bundle. EG4's default poll interval is 15 seconds. | Retain each new source/time observation, even for constant load. Latest eligible source time determines the current state; identical replay is skipped. |
| MPPT detail | Independent controller measurement with tracker provenance. Its outbox identity is aligned with the reading as above. | Already uses source/time uniqueness; retain that index and require identical committed JSON for replay acknowledgement. |
| Energy | A counter observation, including reset evidence, rather than merely a new counter value. `Eg46500ExTelemetrySource.ReadEnergyAsync` keeps the original cached `RecordedAtUtc` between five-minute hardware reads, then timestamps a successful new sample even if the counter is unchanged. The current EG4 outbox bundle contains readings/details rather than energy; this correction does not add an energy sender. | Replaying a cached sample remains idempotent; a genuinely new observation with the same value is retained. A reset/recurring value does not disappear because it existed historically. No new delta or reset inference is introduced. |
| Inventory | An observed inventory/capability snapshot. Both payload and latest response expose observation time; `PowerInventoryConfigurationProvider` uses that time for `IsStale`. | Retain each submitted confirmation at a distinct source/time. Latest source-time state supports A→B→A and refreshed unchanged inventory. No active in-tree collector constructs this payload; no new confirmation cadence is assumed or added. |
| Configuration | A read-only observed settings/command-capability snapshot. The payload has `RecordedAtUtc` and the reader exposes `RecordedAtUtc`/`IsStale`; it is not a command execution endpoint. | Retain distinct source/time confirmations. A producer that emits only changes still produces change history: A→B→A creates three observations. A producer that deliberately reconfirms unchanged A also supplies new freshness evidence, so that confirmation is retained. No active in-tree collector constructs this payload; this change does not turn change-only producers into periodic emitters. |
| Gateway status | A timestamped health/runtime/outbox observation, including freshness evidence in its public response. No active in-tree collector constructs this compatibility payload. | Retain every submitted new source/time observation, including recurring healthy/error states or identical cached nested health content at a new envelope time. Do not infer a successful new health poll from arrival time. |

These types share replay identity but have different sampling/emission meanings. Configuration/inventory are not silently converted into telemetry polling. Nor does the server infer a confirmation from receiving an old change-only event: replaying the same source/time leaves its historical time unchanged. A server-side latest-hash shortcut would need durable confirmation/replay history to preserve both idempotency and freshness. The existing timestamped contracts can retain those facts directly, without adding a last-confirmed field, overwriting old rows or introducing a receipt table.

## Replay, conflicts and reads

Replay identity is the existing normalized `(SourceId, RecordedAtUtc)` within each snapshot table; source ID and time are not replaced by payload content or arrival time. Different sources can report identical content/timestamps independently. Five snapshot tables keep their existing timestamp-stripped SHA256 `PayloadHash` as the committed content proof, without changing its algorithm or historical values. MPPT compares the serialized committed JSON in C# with ordinal equality, avoiding SQL's case-insensitive collation. Same identity plus matching committed content is acknowledged as skipped. Different content at that identity is immutable-conflict failure, HTTP500, and remains unacknowledged/retryable under the existing outbox error contract; submitters must replay the original payload or create a new observation time. The committed row is never replaced.

#400 owns race-path verification after uniqueness violations and transient batch failure propagation. #402 owns pre-insert replay checks and index semantics; both paths must agree before the integrated candidate is qualified. The serialized payload/hash proof intentionally preserves existing serializer/envelope behavior rather than silently introducing a new canonicalization version.

Omitted/default observation times are rejected before timezone conversion can turn the required-input sentinel into a non-default value. This applies to all six snapshot routes and all DateTime kinds, including on non-UTC hosts. Valid real timestamps retain the existing ingest normalization: UTC is unchanged, Local converts to its UTC instant, and Unspecified uses the host-local interpretation. This compatibility decision does not change read-side SQL datetime2 semantics, which restore stored UTC kind without converting wall time.

Latest inventory/configuration/inverter/MPPT/energy/gateway queries exclude missing/default observation times and timestamps beyond `PowerComposition:MaxFutureClockSkewSeconds`. Valid old rows remain available with `IsStale`; stale evidence is not made fresh by arrival order, replay or `CreatedAt`. Eligible latest state is ordered by source observation time, so late historical inserts do not override newer state. Freshness uses the injected current clock and UTC database timestamps. Existing SmartShunt, source-authority policies and public JSON fields are preserved.

## Migration and storage effects

`20261004050923_PreservePowerObservationIdentity` drops the five unique `(SourceId, PayloadHash)` indexes on `v9.PowerDeviceInventorySnapshot`, `PowerConfigurationSnapshot`, `PowerEnergySnapshot`, `PowerInverterDetailSnapshot` and `GatewayStatusSnapshot`. It retains every table/column/row, the unique `(SourceId, RecordedAt)` indexes and the existing time indexes. It neither rewrites historical hashes/JSON/timestamps nor attempts to recover observations previously discarded. MPPT and SmartShunt indexes are unchanged. Source/time indexes still support replay seeks and latest source-time queries; a hash index no longer serves a read/query path.

New distinct-time confirmations increase retained rows compared with historical content deduplication. Budget from the actual submission cadence per source/table: `86400 / intervalSeconds` observations per day. At the EG4 default 15-second cadence, inverter detail can retain up to 5,760 observations/day/source; multiply measured average stored JSON/row bytes and existing index overhead to estimate capacity. Energy's five-minute sample interval would be 288 observations/day/source if an energy sender is wired later. Inventory/configuration growth follows the submitting producer's actual change/confirmation schedule, not the dashboard refresh timer. No retention policy, purge, payload compression or production cadence change is added here; assess disk/backup growth before rollout.

Migration/index DDL requires database schema locks and appropriate migration privileges. Use the normal reviewed migration procedure with a verified coordinated backup and maintenance planning; do not infer rollout authorization from this PR. Apply the migration before admitting new confirmation semantics. Old application code can still read this additive schema, but its historical-hash shortcut will continue dropping recurring states; rolling the application back therefore reintroduces the original defect. On an old schema, repeated content at a new identity can still hit the old hash index, so the integrated #400 duplicate proof must leave it retryable rather than falsely acknowledge it.

Schema downgrade can recreate old unique hash indexes only before repeated content exists. `Down` explicitly refuses with SQL error51000 when any affected source/hash has multiple rows; it never deletes observations to satisfy old uniqueness. If a rollback is necessary after new observations arrive, keep the compatible schema and assess application behavior, use a separately reviewed forward fix, or restore a coordinated pre-upgrade backup while accounting for all post-backup observations. No automatic destructive rollback is provided.

## Qualification

Fast per-type controller/query regressions exercise A→B→A, unchanged confirmations, identical replay, conflicting same-identity payloads, source isolation, late/future/default timestamps and clock-based freshness. All six routes additionally reject omitted/default inputs without persistence and preserve valid UTC/Local/Unspecified instant normalization and immutable replay; run these under both UTC and America/Phoenix processes. The disposable #409 SQL fixture applies the real EF chain on clean and both supported prior checkpoints, compares original IDs/JSON/hash/time/source bytes, admits repeated hashes at distinct times, preserves source/time uniqueness and proves safe downgrade/refusal. Actual SQL controller/provider regressions verify recurring state/freshness and ordinal MPPT replay proof under SQL collation. Retain current-source locked restore/build, fast and SQL reports before independent review; normal post-review CI remains separate. No deployed database or hardware is used.
