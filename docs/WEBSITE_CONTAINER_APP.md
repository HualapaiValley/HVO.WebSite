## Configuration Strategy

Not every value should be handled the same way. The right split is:

| Category | Store In | Examples | Change Model |
|------|------|------|------|
| Secrets | Azure Key Vault | SQL connection string, Application Insights connection string, Entra client secret, API keys | Managed centrally, resolved securely at startup |
| Deployment settings | `appsettings.json` with environment overrides | `ASPNETCORE_URLS`, `EnableHttpsRedirect`, `KeyVault:Uri`, `Telemetry:ServiceName`, listener ports | Set per environment or deployment revision |
| Runtime-editable non-secrets | `v9.SiteConfiguration` | feature flags, thresholds, UI text, polling intervals, operational switches | Change while the app is running |

This is the recommended rule set for the website going forward:

- If a value is secret, keep it in Key Vault.
- If a value defines how the app starts or binds to infrastructure, keep it in appsettings plus environment overrides.
- If a value needs to change without redeploying the app, move it into `v9.SiteConfiguration` instead of adding another environment variable.

## Why Not Use Only Environment Variables

Environment variables work well for local Docker Compose and ACA creation-time settings, but they have an important limitation:

- changing them normally means updating the container definition and restarting or rolling a new revision

That makes them a poor fit for operational values you may want to tune live after deployment.

## Recommended Future Model

The repo already has a `v9.SiteConfiguration` table in the data model, and the website now includes a small cached `ISiteConfigurationService` over that table.

Recommended usage:

- Keep secrets out of the database.
- Use the database table for non-secret settings that admins may need to change at runtime.
- Use `ISiteConfigurationService` as the entry point for runtime-editable website settings.
- Add an admin UI later for editing those values safely.

That gives you:

- Key Vault for secure secret management
- environment variables for deployment shape and infrastructure binding
- database-backed config for live operational changes

## Local Development

Local Docker Compose can keep using environment variables for convenience, but that should not be the long-term home for every configurable value.

For local development:

- keep secrets and per-machine values in `.env`
- keep container listener and HTTPS behavior in Compose env overrides
- treat new runtime-tunable app behavior as `SiteConfiguration` candidates instead of `.env` additions

This avoids the current pattern where every new setting has to be wired through Compose just to make it adjustable.

## Managed Identity Plan

The current deployment uses a user-assigned managed identity.

- Assign `AcrPull` on `hvoobsacr`.
- Assign `Key Vault Secrets User` on `hvoobs-kv`.
- Assign `Key Vault Crypto User` on `hvoobs-kv`.
- Assign `Storage Blob Data Contributor` on `hvoobsdata`.
- Set `AZURE_CLIENT_ID` in the Container App environment to the managed identity client ID so `DefaultAzureCredential` resolves the correct identity during startup.
- Local collector containers can continue using Key Vault-backed secrets through the existing local/developer environment flow until they move to Azure-hosted identities.

## Local Container Development

- Local Docker Compose should continue to enable HTTPS explicitly for browser-based development.
- The website image now needs to stay deployment-dependent:
	- ACA: `ASPNETCORE_URLS=http://+:8080`
	- Local containers: `ASPNETCORE_URLS=https://+:443;http://+:8080`
- Local container HTTPS should continue using the baked self-signed certificate via `ASPNETCORE_Kestrel__Certificates__Default__Path` and `...__Password`.
- `EnableHttpsRedirect` should remain `false` for the local compose stack so the hardware sidecars can keep posting to `http://hvo-website:8080`.
- `HVO_WEBSITE_PUBLIC_BASE_URL` is an explicit local-collector override. If it is unset, Docker Compose keeps collectors pointed at the in-stack website service. Set it in `.env` only when you intentionally want local collectors to post to the deployed ACA website.

## Current Runtime Status

The earlier deployment blockers have been resolved:

- ASP.NET Core Data Protection now uses Azure Blob Storage for persistence and Azure Key Vault for encryption.
- The website Entra app client secret is stored in `hvoobs-kv` as `AzureAd--ClientSecret`.
- The website honors ACA forwarded proxy headers, so OIDC redirects now use the external HTTPS hostname instead of internal HTTP.
- Recent Container App logs no longer show the previous ephemeral or unencrypted Data Protection warnings.

Interactive browser sign-in should now be fully configured, but the final confirmation still requires a real user sign-in through the browser.
